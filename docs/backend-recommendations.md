# Foodies API — рекомендації для бекенд-команди

## 1. Прапорець «в обраному» на рецептах

### Проблема
`GET /api/recipes/{id}` і елементи списків рецептів **не містять** інформації, чи рецепт уже в favorites поточного користувача.

На UI потрібно:
- підсвічувати іконку «серце» на картці;
- показувати «Add to favorites» / «Remove from favorites» на сторінці рецепта.

Зараз фронт змушений:
1. окремо тягнути `GET /api/recipes/favorites` (можливо, кілька сторінок);
2. збирати `id` у пам’яті;
3. звіряти кожен рецепт із цим набором.

Це зайві запити, гонки при пагінації favorites і розсинхрон після відкриття рецепта з іншого місця.

### Пропозиція
Для **авторизованого** користувача додати поле в об’єкти рецептів:

```json
{
  "id": "...",
  "title": "...",
  "isFavorite": true
}
```

Бажано в:
- `GET /api/recipes/{id}`
- `GET /api/recipes` (елементи `data[]`)
- `GET /api/recipes/popular`
- `GET /api/recipes/own` (опційно; для own зазвичай `false` або не потрібне)

Для **неавторизованого** запиту поле можна не віддавати або завжди `false`.

### Альтернатива (гірше, але прийнятно)
`GET /api/recipes/{id}/favorite-status` → `{ "isFavorite": true }`  
Не бажано: +1 запит на кожну картку/сторінку.

## 2. Створення рецепта та зображення (thumb)

### Проблема
ТЗ фронтенду вимагає обов’язкове фото рецепта (file input + preview).  
Контракт create зараз описує JSON-тіло **без** файлу:

- `title`, `category`, `area`, `instructions`, `description`, `time`
- `ingredients`: `[{ "id", "measure" }]`

Неясно, як відправляти зображення і чи воно взагалі підтримується.

### Пропозиція (один із варіантів — зафіксувати в OpenAPI)

**Варіант A (переважний для ТЗ):**  
`POST /api/recipes` як `multipart/form-data`:
- текстові поля як у JSON-контракті;
- `ingredients` — JSON-рядок або повторювані поля `ingredients[i][id]`, `ingredients[i][measure]`;
- файл: `thumb` (image/*).

**Варіант B:**  
1. `POST /api/recipes` (JSON) → створює рецепт;  
2. `PATCH /api/recipes/{id}/thumb` (multipart) → завантажує зображення.

**Варіант C:**  
Створення без фото на API; поле `thumb` завжди `null` до окремого upload — тоді потрібно офіційно послабити ТЗ на фронті.

### Потрібно від бекенду
- Який варіант підтримується зараз?
- Максимальний розмір файлу, MIME-типи, чи є ресайз/Cloudinary тощо.
- Чи `category` і `area` у create — **назви** (`"Dessert"`) чи **id**?

Фронт зараз орієнтується на **назви** в тілі create, як у поточному описі API.

## 3. Єдиний формат ідентифікаторів

### Проблема
У різних джерелах (документація, відповіді) трапляються і `id`, і `_id`.

### Пропозиція
У всіх JSON-відповідях і в OpenAPI — лише **`id`** (string).  
Це прибирає плутанину в TypeScript-моделях і баги мапінгу.

## 4. Списки followers / following — дані для карток профілю

### Проблема
UI профілю (UserCard) очікує багатий прев’ю-контент:
- чи поточний юзер уже підписаний (`isFollowing`);
- кількість власних рецептів;
- інколи прев’ю останніх рецептів (thumb) на tablet/desktop.

Якщо `GET /api/users/{id}/followers` і `GET /api/users/following` повертають лише `{ id, name, avatar }`, фронт робить **N+1 запитів** (профіль кожного + рецепти).

### Пропозиція
Елемент списку:

```json
{
  "id": "...",
  "name": "...",
  "avatar": null,
  "createdRecipesCount": 12,
  "isFollowing": true,
  "recipes": [
    {
      "id": "...",
      "title": "...",
      "thumb": null
    }
  ]
}
```

- `recipes` — опційно, наприклад останні 3–4 для прев’ю;
- `isFollowing` — відносно **поточного** авторизованого користувача;
- пагінація бажана в тому ж форматі, що й рецепти (див. п. 6).

## 5. Формат помилок

### Проблема
Різні shape помилок ускладнюють єдиний toast і валідацію форм.

### Пропозиція
Уніфікувати:

**Загальна помилка:**
```json
{
  "error": "Invalid credentials"
}
```

**Валідація (422):**
```json
{
  "error": "Validation failed",
  "details": {
    "email": ["Invalid email address"],
    "password": ["Too small: expected string to have >= 8 characters"]
  }
}
```

Стабільні HTTP-коди: `400`, `401`, `403`, `404`, `409`, `422` — з передбачуваним тілом.

## 6. Єдина пагінація

### Проблема
Частина ендпоінтів уже повертає:

```json
{
  "data": [],
  "total": 42,
  "page": 1,
  "limit": 10
}
```

Бажано **той самий** shape для:
- `GET /api/recipes`
- `GET /api/recipes/popular`
- `GET /api/recipes/own`
- `GET /api/recipes/favorites`
- списків followers / following (якщо пагінуються)

### Параметри
- `page` — з 1;
- `limit` — з верхньою межею (наприклад 50), значення за замовчуванням зафіксувати в OpenAPI.

## 7. Auth: access / refresh і cookies

### Поточна модель
Login/register повертають у тілі `accessToken`, `refreshToken`, `user`.  
Фронт зберігає токени (persist / localStorage) і шле `Authorization: Bearer <accessToken>`.

### Рекомендація (безпека, середньостроково)
- **refreshToken** — лише в **httpOnly + Secure + SameSite** cookie (виставляє сервер);
- **accessToken** — у тілі відповіді, короткоживучий; фронт тримає в пам’яті;
- `POST /api/auth/refresh` і `POST /api/auth/logout` працюють з cookie;
- CORS: `credentials: true`, явний `Access-Control-Allow-Origin` (не `*`).

Якщо cookie-модель не планується — зафіксувати в OpenAPI, що refresh **завжди** в JSON body, щоб фронт не гадав.

## 8. Popular recipes для блоку на сторінці рецепта

### Потреба UI
Блок «Popular recipes» — невелика кількість карток (типово 4).

### Пропозиція
`GET /api/recipes/popular?page=1&limit=4`  
Гарантувати підтримку `limit` і сортування за популярністю (наприклад, за кількістю favorites), як уже задумано в API.

Поле на кшталт `_count.favorites` корисне для відлагодження, для UI карток не обов’язкове.

## 9. Профіль «me» vs публічний профіль

### Вже зручно
- `GET /api/users/me` — counts (recipes, favorites, followers, following);
- `GET /api/users/{id}` — публічний профіль.

### Уточнити в документації
- Чи `favoritesCount` і `followingCount` доступні лише для `me`, чи також для чужого профілю (у ТЗ UI favorites на чужому профілі можуть не показуватись — це ок).
- Після `PATCH /api/users/avatar` — відповідь `{ "avatar": "url" }` достатня; чи повертається повний user?

## 10. Follow / Unfollow — ідемпотентність і коди

### Пропозиція
| Ситуація | Код |
|----------|-----|
| Успішний follow | `201` або `200` |
| Успішний unfollow | `204` або `200` |
| Вже підписаний | `409` або `400` з зрозумілим `error` |
| Підписка на себе | `400` |
| Не підписаний при unfollow | `404` або `400` |

Фронту важливо не ламати UI на «вже following» — бажано стабільне повідомлення в `error`.
